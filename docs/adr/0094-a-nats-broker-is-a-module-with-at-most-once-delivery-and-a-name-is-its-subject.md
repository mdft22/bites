# A NATS Broker is a module with at-most-once delivery, and a Topic's name is its subject under a prefix

[ADR 0081](0081-a-topic-reaches-other-instances-through-a-broker-and-postgres-is-a-module.md) made a Topic reach the other instances through a `Broker` and built the Postgres one. An application whose instances share NATS rather than a database, or whose fan-out Postgres's `NOTIFY` cannot carry (the 7999 bytes of a notification, one channel read by every instance), had to write a Broker itself and meet the same bugs: a connection that drops and is never reopened, a message over the server's limit that kills the connection, a `Publish` made while the connection is down that is buffered and sent later and out of order, a subject with a wildcard or a space that a key from data made. Decided on 2026-11-17 and built (`modules/natsbroker`).

**Decision.**

- **`modules/natsbroker` is the NATS Broker**, a module with its own `go.mod` and `github.com/nats-io/nats.go` ([ADR 0006](0006-no-third-party-dependency-in-the-core.md), [ADR 0070](0070-optional-features-are-modules-under-modules-each-with-its-own-go-mod.md)). It has the shape of `pgnotify` so that an agent who knows one uses the other: `natsbroker.New(Options)` returns a `*Broker` and connects nothing, `Run(ctx)` holds the connection and blocks, `Close()` stops it, `Listening()` and `Options.OnState` say whether it is live, and `MinBackoff`, `MaxBackoff` and `PublishTimeout` mean what they do there. `Options.URL` is required (one server or several of a cluster separated by commas, with the scheme `nats`, `tls`, `ws` or `wss`), and `Options.ConnectOptions` is a list of `nats.Option` for what the Broker does not decide (TLS, credentials, a connection name) and is applied before the Broker's own settings, so reconnection, publish buffering, echo, the ping interval and every handler are the Broker's whatever it holds. Under a lifecycle Service it is `Start: go broker.Run(ctx)` and `Stop: broker.Close`, as ADR 0081 says for `pgnotify`.
- **Delivery is at most once, and the module says so where it is read.** Core NATS publish and subscribe keeps nothing: a message reaches each instance that is subscribed and connected when the server routes it, once, and no one else, and a message that cannot be given to an instance too slow to read it is dropped by the client or the server. The Broker's contract already has the signal for this, the `gap`, and the module calls it in the two cases where the client knows it lost messages: the connection dropped and came back (the subscriptions that were live, and those made while it was down or before the first connection, are told once the connection is live again, as `pgnotify`'s are), and NATS dropped messages because the deliveries ran behind (every subscription is told, since one subscription carries every name, and a Warn names the limits). A message published while an instance was disconnected is the instance's gap and not its message: the application has the place to read it from (the history route), exactly as ADR 0081 requires of `pgnotify`. The package comment, `Publish`'s and `Subscribe`'s comments, and the reference page state "at most once".
- **JetStream is not used, and the module needs none.** JetStream would make delivery at least once with replay, and that changes what the interface means: an instance would need a durable or ephemeral consumer of its own to resume from, a stream with a retention, cleanup of the consumers of instances that never come back, acknowledgements, and de-duplication of redeliveries, none of which `Broker` has a method for (`Subscribe` takes no position and `deliver` no acknowledgement), and a Topic whose messages are replayed after a gap would deliver stale frames the application's history route already supplies. The Broker contract promises no durability (a gap exists because of it), so the cheapest transport that keeps the other promises is the right one. If the interface ever gains durability, a JetStream Broker sits behind it with a `gap` that rarely fires, as ADR 0081 says of a durable stream; that is a decision of its own.
- **A Topic's name becomes the subject `Prefix + "." + name`, unchanged, and a name NATS would read differently is refused, never escaped.** `Options.Prefix` is `bites` when empty, so `room.7` is the subject `bites.room.7`, `nats sub "bites.>"` shows an application's traffic and a subject permission `bites.>` fits one application; applications that share a server use different prefixes. `Accepts` refuses what a subject cannot carry or what NATS reads as something else: an empty name, over 255 bytes, invalid UTF-8, a space or control character, a `*` or `>` (wildcards, so a key such as `>` would hear every room's messages and a publish to `room.*` would reach nobody), and an empty part (a leading, trailing or doubled dot). The message names the character and what to change: `the name has '>' at byte 4, which NATS reads as a wildcard, so it would hear or send other names' messages: remove it, or encode a key that comes from data (hex, or base64.RawURLEncoding) before it is put in a name`. A [`Topics`](0084-a-name-made-from-data-is-a-key-of-a-topics-family.md) family returns it from `Subscribe` and `Publish` for a key from data, which is where ADR 0084 puts the check, and `NewTopic` panics with it at Registration. `Options.Prefix` has the same rule at `natsbroker.New`, and refuses a leading `$` and `_INBOX`, which NATS reserves. Escaping was rejected: a mapping from any name to a subject must be injective and leave `.` as the separator, so it grows rules for the empty part, for `%` and for the wildcards, the subject an operator reads is no longer the name the code wrote, and a key with a space then works on NATS and is refused by `pgnotify`, so the first deployment on one broker is a bug on the other; a refusal is the same on both and an agent fixes the key once, at the family.
- **One subscription carries every name, and a name with no Topic is dropped on arrival.** Each instance subscribes to `Prefix + ".>"` when it connects and keeps a map of the names that have a subscriber, as `pgnotify` holds one `LISTEN`. A subscription for each name was built first and rejected: NATS routes a name to an instance only while a Topic of it listens, which is the better use of the network, but a subscription is live at the server only after a round trip, `Broker.Subscribe` must not block on the network, and so a message a peer published right after a Socket joined was lost, silently, which `bitetest.TestBroker` found in its first subtest ("a Publish reaches a subscription on a peer Broker", 5 s with nothing delivered). With one subscription made before the connection is reported live (and confirmed with a round trip before `Listening` is true), a subscription made while the connection is up hears the next message published to its name, the window is zero, and `Subscribe` and `stop` touch a map and nothing else. The price is the one ADR 0081 states for Postgres: every instance is sent every name's messages and drops those it has no Topic for, so at a rate the network or an instance cannot take for all names, a prefix for each shard of names is the next step.
- **`Publish` waits for the server and refuses while there is no connection.** It publishes and then waits for the server to confirm it holds the message (a flush, bounded by `PublishTimeout`, 5 s by default), so a connection that dropped under the message is an error and not a `nil`. With no live connection (before `Run` has connected, while it reconnects) it returns `ErrNotConnected`, wrapped with the client's state, and sends nothing: the client's reconnect buffer is turned off, because a message kept for later arrives after the gap that told the application to reload and out of order with the messages that followed, which is a silent surprise ([principle 2](0077-four-principles-in-the-order-they-win.md)). `ErrClosed` follows `Close`. A payload over the server's `max_payload` (1 MiB unless the server is set otherwise, read from the server when connected) is a `*bites.PayloadError` whose `Limit` is that number, checked before anything is sent, since the server closes a connection that sends more; NATS counts the payload only, so nothing is taken off for the name. `Subscribe` of a name `Accepts` refuses is logged at Error and delivers nothing, since a Topic never asks.
- **The connection is the client's, with the Broker's settings.** `nats.go` reconnects by itself; the Broker has it retry the first connection too (`Run` does not wait for it: the instance reports itself not ready through `OnState` until it is live), forever, with the pause of `pgnotify` (100 ms doubling to 10 s, 20% jitter), each failure logged at Warn with the error and `retry_in`, each connection at Info, and pings an idle connection every `KeepAlive` (30 s) so one dropped without a reset is found in at most three periods. An unrecoverable end (the client gives up for good, which it does after repeated authentication failures) makes `Run` return the error, and `Publish` then says it is not connected. A permission violation for a subject, or any other asynchronous error, is logged at Warn with the error.
- **Ordering is a publisher's own, and one server's.** A publisher that waits for each `Publish` is heard in its order on every instance, and the suite holds that. On one server every instance hears one order for a name; in a cluster the servers route independently, so two publishers racing may be heard in different orders on two instances, which ADR 0081 states for Postgres as "the same on every instance" and is weaker here (stated in the reference). A Topic's messages that must be ordered across publishers carry a sequence the application orders by.
- **Every payload is the subscriber's to keep.** The first subscriber of a name gets the bytes of the client's message, which are its own copy, and each further subscriber of the same name on the instance gets a clone, as the interface requires and the suite checks.

**Refusals** (rows of `modules/natsbroker/natsbroker_test.go`, each ending `registered at <file:line>`; the Topic's own rows are in ADR 0081):

- `natsbroker.New: URL is empty: give the NATS server, such as nats://127.0.0.1:4222, or several of a cluster separated by commas`; a URL with no scheme, with a scheme other than `nats`, `tls`, `ws` or `wss`, or with no host.
- `natsbroker.New: Prefix "app.>" is not a NATS subject prefix: Prefix has '>' at byte 4, which NATS reads as a wildcard ...`, and a space, an empty part, over 64 bytes, a leading `$` or `_INBOX`.
- `natsbroker.New: MaxBackoff 1ms is below MinBackoff 1s: give a maximum at least the minimum`, and a negative duration.
- `NewTopic "room.*": the broker does not carry this name: the name has '*' at byte 5, which NATS reads as a wildcard ...` (the row of ADR 0081 for a name the broker refuses), and for a key of a family, the error of `Topics.Subscribe` and `Topics.Publish`: `bites: Topics "room.": the broker does not carry the key ">": ...`.

**What it costs** ([ADR 0003](0003-the-trade-budget.md)). Core: none. No file of the root module changes, so allocations per request and memory per idle connection do not move, and neither does a Topic's publish path, which already hands bytes to a Broker. The module's own cost is one NATS connection and one subscription for an instance, a copy of each message the instance is sent (the client's), and a map read to drop a name nobody listens to; a `Publish` costs one round trip to the server. These are not measured here: the module adds no work to a request, and the round trip is the contract of `Publish` (ADR 0081), so no row of the table changes.

**Scenarios it was put against.**

- _The connection is cut and returns (a proxy that closes the sockets, a server restart)._ `OnState(false)`, a Warn with the error, `Publish` returns `ErrNotConnected` and keeps nothing, the client reconnects, `OnState(true)`, then each subscription's `gap` runs once, and a message a peer published during the cut is not delivered (at most once): tested against a real server through a proxy that is cut and held.
- _A Topic's first Socket joins and a peer publishes at once._ Heard, since the subscription to the prefix already exists; held by the conformance suite.
- _A key from data is `>`, `*`, `a b` or `7..8`._ The family returns the broker's error from `Subscribe` and `Publish` and sends and subscribes nothing; a plain client on the same server cannot be made to hear another room.
- _Another application on the same server._ A different `Prefix` is a different set of subjects: an instance does not hear it, held by a test with a plain client on `Prefix.>`.
- _A slow consumer._ A deliver that blocks while 70000 messages arrive makes NATS drop what exceeds 65536 messages or 64 MiB, the gap runs and a Warn says why; the other instances are unaffected.
- _A message of exactly the server's limit and one byte over._ The first is carried and the second is a `*bites.PayloadError` with that `Limit` and nothing sent, held by the suite with the limit read from the server.
- _A caller passes `nats.NoEcho()`._ The Broker's settings replace it, so the instance still hears its own publishes; tested (a `nats.MaxReconnects` of the caller is replaced the same way, by the order the options are applied, and is not tested separately).

**What it fails at.**

- **At most once is a different promise from Postgres's in one respect only: nothing is kept for an instance that is down in either, but NATS also drops for a slow one.** An application that needs a message to survive an instance's absence needs a history it can read, as ADR 0081 says; this broker does not make that less true.
- **Every instance is sent every name.** With one subscription for the prefix, an instance with Sockets in 1% of the names receives all of them and drops 99%. It is the cost accepted for a subscription with no window, and the first thing to give when the volume of an application asks: a prefix for each shard of names (two Brokers and a Topic that picks one), or a per-name subscription made safe by waiting for the server on the first Socket of a name, which this interface cannot do without blocking.
- **A cluster orders two racing publishers on each server.** One order for a name is not promised across instances on different servers.
- **The first connection is not waited for.** `Run` returns the error of a bad option, but a wrong URL, a refused credential that the client retries, or a server that is down is a log line and `Listening()` false, not an error of `Run`; an application that must not serve without NATS fails its readiness from `OnState`, as ADR 0081 describes. If the client gives up for good, `Run` returns that error; that path is written from the client's documented behaviour and is not tested.
- **A `Publish` that returns nil says the server has the message, not that any instance heard it.** NATS core has no acknowledgement from subscribers.
- **Not tested here:** a NATS cluster, TLS, credentials files and WebSocket transports (the module passes `ConnectOptions` through and tests none), and the server's own slow-consumer disconnect of an instance (the client reconnects and the gap follows, which the proxy test exercises from the other side).

**Considered and what was rejected.**

- **One subscription for each name:** above; correct for routing and wrong for the first message after a join.
- **JetStream:** above; durability the interface has no method for.
- **Escaping a name into a subject:** above; the refusal is one rule for both brokers.
- **The client's reconnect buffer:** sends a message after the gap and out of order, in silence.
- **A `Publish` that returns when the client has buffered it:** a connection that dropped under the message is a `nil`; the round trip is the price of an error that means something.
- **A `*nats.Conn` given by the application, as `pgnotify` takes a pool:** the Broker needs its handlers on the connection (disconnect, reconnect, closed, asynchronous errors) for the gap and `OnState`, and a given connection's handlers are the application's; `ConnectOptions` carries what an application needs to connect.
- **Named for the transport (`modules/nats`):** the package would shadow the client's own `nats` import in every file that uses both.
