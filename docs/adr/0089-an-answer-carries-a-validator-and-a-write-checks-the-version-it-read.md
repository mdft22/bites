# An answer carries a validator, a read revalidates with a 304, and a write checks the version it read with If-Match

A JSON answer can carry the version of what it holds, and the two things that version is for are typed: a `Tagged[T]` return sends it, and answers a GET whose `If-None-Match` names it with a 304 and no body; an `IfMatch` field in a write's Header section carries the version the client read, and the handler checks it against the current one with `Check`, which is a 412 problem+json when it is stale and a 428 when the request named none. Built 2026-11-17 (from the roadmap, Fairly important). `File` has done this for its own answers since [ADR 0064](0064-a-file-answers-its-own-conditional-and-range-requests.md); this is the same protocol for a record the application owns, where the version is the application's and not a modification time. Measurements: [`docs/research/etag/`](../research/etag/report.md).

**The surface is three names and a constructor, each typed.** `ETag{Version string, Weak bool}` is the validator; `Tagged[T]{Body, ETag, Header, Cookies}` is a 200 return that carries it; `IfMatch` is the Header field of a write; `ETagOfBody()` asks the framework to make the tag from the JSON it writes. A handler reads and writes the same text for the same record, `ETag{Version: v}` on the way out and `in.Header.IfMatch.Check(v)` on the way in, so there is no quoting to get wrong and no `W/` to forget. An agent that sees only the signatures sees `Tagged` where a plain value was and `IfMatch` where a header goes, and the refusals below say what to change when it misplaces either.

**A `Tagged` is its own return type, not a field of `OK` or a route option.** The Location argument of [ADR 0013](0013-other-statuses-are-wrapper-types.md) went the other way, and for a reason that does not hold here: a `Created` may leave `Location` empty, so the type could not say whether the header is sent and a route option had to. A `Tagged` always sends its `ETag` (an empty one is a logged 500), so the type does say it, and Registration reads it: the API document states the `ETag` header as required on the 200 and a 304 on a GET or HEAD route with nothing the handler declared. An `ETag` field on `OK[T]` was rejected because it would be sent sometimes and the document could not say when; an `ETag` in `Header`, which `OK` still sends as any other header, is not evaluated, and a `Tagged` that also has one is a logged 500, so the evaluated tag has one place.

**The tag, and strong against weak.** `Version` is 1 to 128 visible characters without a double quote, which is what RFC 9110's `etagc` allows; the framework puts the quotes on, and `W/` before them when `Weak` is set. The zero value is strong, because a strong tag is the only kind a write can be made conditional on and the safe default is the one that works for both uses. A `Version` that cannot be in a tag, or is empty, is a 500 logged with the field to change, per response, like a bad `ETag` in a `File`'s `Header` ([ADR 0064](0064-a-file-answers-its-own-conditional-and-range-requests.md)), because it is a value the handler computes and Registration cannot see. The wire form is built on the stack: a version given by the handler costs the answer no allocation.

**A read: 304 before anything is encoded, when the handler gave the version.** On a GET or HEAD route a `Tagged` is compared with the request's `If-None-Match` by the weak comparison of RFC 9110 section 13.1.2 (`W/` ignored, `*` matches, a list is read by its quotes because an opaque tag may hold a comma), reusing `conditional.go`'s parser, which is the one `File` uses. A match is a 304 with the `ETag`, the `Cache-Control`, `Content-Location`, `Expires` and `Vary` of `Header`, any `Last-Modified` the handler put there, the cookies, no `Content-Type` and no body: the body is not encoded, so a client that already has the record costs the head. A header that does not parse names nothing and the answer is a 200, as RFC 9110 section 13.1 allows for a precondition the recipient cannot read; it is the safe side for a read, and the opposite of what `If-Match` does below. On every other method the tag is only sent and `If-None-Match` is not evaluated: a PUT that answers with the record it changed carries the new version, and a 304 there would drop the change from the client's sight. `If-Match` on a GET, and `If-Modified-Since` and `If-Unmodified-Since` on any `Tagged` (it has no modification time), are not evaluated; `If-Match` is the write's precondition and is the handler's, and a conditional GET by date is a `File`'s.

**`ETagOfBody()`: a weak tag of a SHA-256 of the encoded body.** For an answer whose handler has no version (a report, a list assembled from several rows) the framework encodes the body as it always does, hashes it in place and sends `W/"` + the first 16 bytes of the digest in unpadded base64url (22 characters) + `"`. It is weak, because the bytes that reach the client can change after the tag is made (compression, [ADR 0031](0031-gzip-only-and-off-by-default.md), and any proxy that recompresses or rewrites), and it is made before compression, so one answer has one tag whichever coding the client gets. It is stable across instances and restarts (no per-process seed), which `hash/maphash` is not. It needs the whole body encoded first, so its 304 saves the write and not the encode. SHA-256 (hardware accelerated, 2.5 GB/s here, no allocation: `sha256.Sum256` returns an array) was chosen over a faster non-cryptographic hash because a body can contain text a client chose, and a collision for CRC-32 or FNV is one an attacker can make, which would serve a client its stale copy; the table is in the report. It is not the version of a write: the handler does not know it, so a client's `If-Match` cannot be checked against it, and the documentation says so where the constructor is. A tag made from every JSON body without being asked, as Fiber's and Hertz's `etag` middleware does, was rejected for the reason [ADR 0022](0022-middleware-sees-a-request-view-and-returns-a-response-value.md) already gives (a middleware cannot hash a body) and by [ADR 0003](0003-the-trade-budget.md): it would add a pass over every answer of every route, with a cost that grows with the size of the body, to give a tag the handler could not use for a write.

**A write: `IfMatch` is a field, absence is the zero value, and `Check` is the handler's.** The field must be named `IfMatch` and sit in a Header section; its type is parsed by the framework's own decoder, which keeps the value as the slab holds it (no copy, no `UnmarshalText` call). A request with no `If-Match` leaves the zero `IfMatch`, which `Present()` reports as false. `Check(version)` compares the header with the record's current version:

- no `If-Match` is a **428 Precondition Required** ([RFC 6585](https://www.rfc-editor.org/rfc/rfc6585#section-3)), `PreconditionRequired` of [ADR 0049](0049-errors-are-found-with-errors-as-and-timeouts-wait.md), a problem+json as every error answer is ([ADR 0012](0012-client-errors-are-400-problem-json.md)), whose detail says to send `If-Match` and where to get the ETag;
- a header that names no tag equal to `version` is a **412 Precondition Failed**, whose detail says to GET the record again, apply the change to what was read and send the new ETag;
- `*` matches, because the handler calls `Check` once the record exists and answers 404 before it;
- a version that cannot be in a tag is an ordinary error (a 500), not a 412, since it is the handler's bug.

A handler that accepts a write with no precondition asks `Present()` and skips `Check`; there is no second spelling for "optional", because a bare `IfMatch` already reads as absent and `Opt[IfMatch]` is refused. The 428 is the framework's default for the route that wants one and says so by calling `Check` unconditionally, and was chosen over a 400 for a missing header because the type of the field, not the section it sits in, decides how its absence is answered, and 428 is the status the RFC defines for exactly this.

**`Check` ignores `W/`, a deliberate departure from RFC 9110 section 13.1.1.** The RFC says `If-Match` uses the strong comparison, which a weak tag never satisfies. [ADR 0031](0031-gzip-only-and-off-by-default.md) weakens a strong `ETag` when, and only when, the body is compressed, and an intermediary such as nginx does the same, so with gzip on a client receives `W/"3"` for the strong tag `"3"` and sends back what it got. With the strong comparison every write would be a 412 behind compression, for a reason nothing the client or the handler did could repair. What the comparison protects, that two representations are not mistaken for one, does not apply to a write whose tag names a version of the record and not of its bytes: equal opaque text is the same version. A proxy that strips `W/` instead is accepted for the same reason. `File` keeps the strong comparison, because its tag is made by the engine, is never weakened (a `File` is never compressed) and names bytes, which `If-Range` needs.

**An `If-Match` that cannot be read is a 400, never ignored.** Ignoring a precondition is allowed for a read and would make a write unconditional, so a value that is not `*` or a list of quoted entity-tags is a 400 located at `header.If-Match` with the sentence `expected * or entity-tags such as "3" or W/"3", separated by commas`. A value over 1024 bytes and a list of more than 16 tags are 400s of their own (`expected at most 1024 bytes`, `expected at most 16 entity-tags`), on by default as every limit is ([ADR 0024](0024-limits-are-on-by-default.md)): a client names one version, and the scan of `Check` is bounded by this length and not by the head's 8 KiB. A second `If-Match` line is the existing 400 `sent more than once` of any non-list header, which keeps the value one string; a proxy that splits a list across lines would meet it, and the fix is the one line.

**The check is the handler's because only the handler can make it atomic with the write.** A framework that compared before calling the handler (a route option taking a function that loads the current version) would read the record twice and leave a window between its check and the handler's write in which another request writes, which is the bug this feature exists to prevent, now hidden behind a framework that claims to have handled it. So `Check` is called inside the handler, after it has the record in hand, and the guide shows the two patterns that make the pair atomic: the row locked in a transaction, or an `UPDATE` whose `WHERE` names the version just checked and an answer of 0 rows affected returned as the 412. The doc comment of `IfMatch` says it.

**A handler that declares the field and never asks is told in the log, on every success.** The silent failure of this design is a route that has an `IfMatch` field and writes unconditionally, which is the lost update it was added to stop and which no compile or Registration step can see. At decode, each `IfMatch` field is given one byte of the request's slab (the storage of every string in the Input, so nothing pooled reaches user code, [ADR 0008](0008-no-pooled-object-reaches-the-user.md)); `Present` and `Check` set it; when the handler returns with no error and the byte is still zero, the log gets a warning that names the field, the method and the path and says to call `Check` with the record's current version before writing. The answer is not changed, because the write has happened and a 500 would only report a change as failed that was made. A route with no `IfMatch` field pays one nil comparison per call and per decode.

**What the API document says.** An `IfMatch` field is an optional string `header` parameter named `If-Match`, with a description of what it means and what its absence and its mismatch answer; the route's responses gain a 412 and a 428 (`Error` problem), stated from the type of the field because the handler's `Check` is where they come from. A `Tagged` states `ETag` as a required header of its 200, and a GET or HEAD route a 304 that carries it; a `Tagged` on any other method states no 304. `ErrorStatus[T](412)` or `(428)` on such a route is refused by the existing rule that the document does not restate a status the framework already answers on the route; `ErrorStatuses(412)` is accepted and changes nothing.

**What it costs** ([ADR 0003](0003-the-trade-budget.md); the run is [`docs/research/etag/report.md`](../research/etag/report.md), AMD Ryzen 7 9700X, 2026-11-17, `taskset` on cores 2,3,10,11).

- **Allocations: none added.** A typed GET returning a `Tagged` with a version, the same with a body tag, the 304 of the version, and a PUT that decodes `If-Match`, calls `Check` and returns a `Tagged` all measure **2.00** over the in-memory connection, the row of a typed route (`TestATaggedGetItsMatching304AndATagMadeFromTheBodyAllocateTwice`, `TestAPutThatChecksIfMatchAndAnswersATaggedAllocatesTwice` in `etag_budget_test.go`). The wire tag is built in a 136-byte stack buffer, the digest is an array, the `IfMatch` byte comes from the slab, and `IfMatch` stores the header's slab string without a copy. The version string a handler makes from a number (`strconv.FormatInt` above 99) is the handler's allocation, not the framework's.
- **Idle memory per connection: none.** No connection field was added.
- **Time:** a version tag is not measurable against a plain return; a body tag adds the hash, +0.6 µs for a 0.8 KB body and about +3 µs for 8 KB, the 3.3 µs the microbenchmark gives SHA-256 over 8 KB, with a spread that is large on that row (5 to 13 µs, the machine's noise, in the report); the 304 of a version is about 1 µs (1.0 to 1.2 for 0.8 KB, 1 to 4.8 for 8 KB) against 1.8 and 5.9 µs for the answer it replaces. Throughput and p99 of a route that uses none of this: not measured, and the code on its path is a comparison of the plan's kind in `write` and a nil check in `decode` and in `call`.
- **Binary size:** not measured.

**Refusals.** Registration refuses, each with a row in the refusal table of `refusal_test.go`: an `IfMatch` in a Path, Query, Cookie or Form section (`... is an IfMatch, which is the If-Match header, so it belongs in the Header section and not in a Query section`); an `IfMatch` field with another wire name, through `WireNames` or a field called anything but `IfMatch` (`... is an IfMatch but its wire name is "Match": ...`); an `Opt[IfMatch]` (`... is already absent when the request sent no If-Match: make the field an IfMatch and ask Present() in the handler`); and a list of `IfMatch` (`If-Match is one header whose value is already a list of entity-tags`). What cannot be caught before the first request, being values the handler computes, is a logged 500 per response with the message that names the change: an empty `ETag` on a `Tagged`, a `Version` that cannot be in a tag, an `ETag` in a `Tagged`'s `Header` as well, and a `Check` given a bad version. And what no step can catch is the handler that never calls `Check`, which the log line above reports.

**Scenarios it was put against.**

- _Two clients overwrite one record_ (the trigger): both GET `"1"`; the first PUT with `If-Match: "1"` answers `"2"`; the second PUT, still `"1"`, is a 412 that changed nothing; it GETs again and succeeds with `"2"`. `TestTwoClientsOverwritingOneRecordTheSecondGetsA412UntilItReadsAgain`.
- _A write that sends no `If-Match`_: a 428 on a route that calls `Check`, the write not made; a route that asks `Present` first writes unconditionally and is not logged; a route that never asks is logged on each success.
- _A hostile client sends a huge `If-Match`_: past 1024 bytes or 16 tags it is a 400 before the handler runs, so the scan of `Check` is bounded; a huge `If-None-Match` on a GET is not refused (a read ignores what it cannot use) and is bounded by the head limit of 8 KiB, the scan being the one `File` already does ([ADR 0064](0064-a-file-answers-its-own-conditional-and-range-requests.md)); a list of a thousand tags that ends with the tag is a 304, in one pass.
- _A proxy weakens or strips the weak marker_: with `WithGzip` the answer carries `W/"1"`, the client sends `If-Match: W/"1"` and the write is accepted; a stripped `W/` is accepted too; neither makes a stale version match.
- _The same record behind two instances_: a `Version` taken from the row is the same on both; a body tag is stable (no process seed), so both give the same tag for the same bytes, provided they encode the same bytes, which the same code and the same data do (not verified across versions of the application).
- _The reference workload_ ([ADR 0002](0002-the-reference-workload.md)): a room's settings edited by two moderators is the first case; the room list a client polls is a `Tagged` with a body tag and a `Cache-Control: no-cache`, answered with a 304 of about a microsecond.
- _A private answer behind a shared cache_: a 304 is sent to anyone who holds the tag, so a record that differs by user must carry `Vary` (or `Cache-Control: private`) in `Header`, which the 304 keeps; the guide says so.

**What it fails at.**

- **The check and the write are two steps.** `Check` compares a version the handler read; a write that does not lock the row or compare the version in its `WHERE` can still lose an update between them, as in any application-level optimistic scheme. The framework cannot make it atomic and says so rather than imply it.
- **A handler can forget `Check`**, and only the log says so.
- **`Check` ignores `W/`**, so a handler that deliberately gives weak tags for a different meaning (the same state, different bytes) and wants a write to tell them apart cannot; every use of tags in this framework for a write is of a version of a record.
- **A body tag is as stable as the bytes.** A body that includes a field that changes on every encode (a server time, a request ID, an unordered list) gives a new tag each time, so its 304 never fires; the tag does not know what the handler meant by "changed".
- **A body tag costs a pass over the body and saves no encode**; only a handler-given version avoids the encode on a 304.
- **A 304 is decided by one header.** There is no `If-Modified-Since` for a `Tagged`, so a client that has only a date gets the body.
- **Create-only is not built.** `If-None-Match: *` on a PUT (create only if absent) needs the header in the Input, which this does not give; a handler answers it with its own check or a unique key until a trigger asks.
- **A second `If-Match` line is a 400**, which a proxy that splits a list would meet.
- **`If-Match` on a GET is ignored**, which RFC 9110 section 13.2.2 does not allow a server that evaluates preconditions to do; a 412 for a read is of no use to an application that is not resuming a ranged download, and a `File` does it.
- **The version is a handler's string**, not verified to change: a handler that returns the same `Version` after a change gives its clients 304s of stale data, as in every system whose version the application chooses.

**What was rejected.** A route option that gives the framework a function returning the record's current version and makes it do the check before the handler (a race window, a second read, and a promise of atomicity the framework cannot keep; above). An `ETag` field on `OK[T]` and a route option `Validated()` (the header would be sometimes sent and the document could not say when; above). A tag made for every JSON answer, by an engine pass or a middleware (above, and [ADR 0022](0022-middleware-sees-a-request-view-and-returns-a-response-value.md)). The strong comparison for `If-Match` (every write a 412 behind compression; above). `ETag` as a string with `StrongETag` and `WeakETag` constructors, which allocates a string for every tag the handler makes and lets a malformed one in; the struct is built in the framework's buffer. `Opt[IfMatch]` for "may be absent", which is a second spelling of what a zero `IfMatch` already says. A 400 for a missing `If-Match` through the field being required (the status of an absent precondition is 428, and the field's type, not the generic "required", is what knows it). Returning the current ETag in the 412, which would tell a write-only client a version it cannot read. A weak tag from a hash by default for strong uses: `If-Match` needs the version, not the bytes, so a tag made of the bytes is the wrong tag for the write.
