# A cron schedule is a Service read in a given zone, and a job lock lets one instance run each occurrence

`Every` calls a function once per interval from the moment the app started ([ADR 0079](0079-services-start-after-the-app-binds-and-stop-in-reverse-around-shutdown.md)), which cannot say "at 02:30 every day" or "on weekdays at nine", and which runs on every instance of an application, so a job that must happen once (a report, a billing run, a mail) needed a lock the application wrote itself. A schedule at a time of day brings three things the interval never had to decide: which zone the time is read in, what happens on the two nights a year the zone's offset changes, and what a run does when the clock does not move the way the timer says. Decided and built on 2026-11-17 (`cron.go`, `cronspec.go`, `joblock.go`, `bitetest/joblock.go`). It is the roadmap's "a schedule beyond a fixed interval", and it edits ADR 0079 where that ADR left cron out.

**Decision.**

- **`Cron` is a third constructor of a `Service`, beside `Worker` and `Every`, and the only way to a schedule at a clock time.** `func Cron(name, spec string, loc *time.Location, fn func(ctx context.Context) error, opts ...CronOptions) Service`, registered with `app.Service`. It has the same `ctx` as `Every` (the Service's life, with the app's clock and logger), the same `Stop` that waits for a run in progress, and the same handling of what `fn` does: an error is logged at Warn and the schedule goes on, a panic is recovered and logged at Error with its stack and the schedule goes on.

  ```go
  jkt, _ := time.LoadLocation("Asia/Jakarta")
  app.Service(bites.Cron("daily-report", "30 2 * * *", jkt, func(ctx context.Context) error {
      return reports.Build(ctx, bites.ScheduledAt(ctx))
  }, bites.CronOptions{Lock: lock}))
  ```

- **The spec is the five fields of cron, written by hand in the core, about 350 lines, with no dependency** ([ADR 0006](0006-no-third-party-dependency-in-the-core.md)): minute, hour, day of month, month, day of week; each a `*`, a number, a range, a list of those, and `*` or a range with a step (`*/15`, `10-40/10`); months and days as three-letter names (`jan`, `mon`); `7` as Sunday. The shortcuts are `@yearly`, `@annually`, `@monthly`, `@weekly`, `@daily`, `@midnight` and `@hourly`. When both the day of month and the day of week name days (neither starts with `*`), a day matches either one, as in Vixie cron; when one is `*` the day must match both. A spec is read once, at the call, and a spec no date of nine years satisfies (the 31st of February) is refused there.
- **The syntax is the standard one and refuses what it does not take, with the text to write instead.** No seconds field (the smallest step is a minute; a shorter interval is `Every`), no `?`, `L`, `W` or `#`, no `a/n` without a range (the message says `5-59/15`), no range that runs backwards (the message says to write two). **`@every` is refused**: an interval is `Every`, one way to do a thing ([ADR 0077](0077-four-principles-in-the-order-they-win.md)), and an interval has no clock time to line up, so two instances would run it at different moments and the lock below could not make them share a run.
- **The time zone is a required argument and the machine's is refused.** `loc` must be a `*time.Location` the application chose: `time.UTC` or the result of `time.LoadLocation`. `nil` is refused, and so is `time.Local`, because a schedule read in the machine's zone is a different schedule on another machine, and an image built with no `TZ` is UTC without anyone having said so (nothing is defaulted in silence, [principle 2](0077-four-principles-in-the-order-they-win.md)). Loading a zone is the application's call, so its error is the application's; `import _ "time/tzdata"` is the application's choice for an image with no zone files. The start-up line of a job names its zone, and every time in a log line is shown in it.
- **Daylight saving has one rule, written once in `cronSpec.next`.** A spec that names hours (`30 2 * * *`, `0 9-17 * * mon-fri`, `0 */2 * * *`) is a time of day, and runs once for each calendar day the time can happen on:
  - a time that **does not exist** that day (the clocks went forward over it) runs once, at the first instant after the gap: `30 2 * * *` on the day 02:00 becomes 03:00 runs at 03:00, and so does `0,30 2 * * *`, once, not twice. The day is not skipped, because a daily billing run that misses one night a year is the failure nobody sees.
  - a time that **occurs twice** (the clocks went back over it) runs once, at its first occurrence, and not again an hour later.
  A spec that has every hour set (`@hourly`, `*/15 * * * *`, `5 * * * *`) is a rate that follows the clock: a time that does not exist is not run (the hour that was skipped had no `:05` in it), and a time that occurs twice runs twice (the hour that repeats has two). The two rules differ because the two kinds of job differ: a time of day is about the day, a rate is about the minutes that pass. Both are tested against an injected clock and the zones that matter (America/New_York, Europe/London, Australia/Sydney, Australia/Lord_Howe with its half hour, America/Sao_Paulo whose change was at midnight), and a test counts the runs of seven specs on every calendar day of a year in six zones.
- **The schedule keeps its own time, so a slow job does not move it.** The timer for the next occurrence is armed when an occurrence comes due, before its run starts, and a run is its own goroutine. There is **no run at start** (the first occurrence is the first time after the app started serving, and the start-up line says when), because a time of day has no "now" to run at, and a job that must also run at start is a `Worker` or an `Every` with `AtStart`. `Start` never waits for work.
- **Runs never overlap, and what the schedule passes is dropped, not queued.** An occurrence that comes due while the last run is still going is skipped and logged at Warn at that moment (`bites: job skipped: its last run is still going`, with `job`, `due` and how many were `dropped`), not when the long run ends, so an operator sees a hung job minute by minute. This is `Every`'s rule ([ADR 0079](0079-services-start-after-the-app-binds-and-stop-in-reverse-around-shutdown.md)) with the same reason: a catch-up burst hits a database exactly when it is slow.
- **A missed time after a pause is skipped and logged, never run late and never in a burst.** A run starts at its due time or within a minute after it (`cronGrace`). When the timer fires more than that after the time it was set for (a suspended laptop, a stopped container, a clock stepped forward), that occurrence is skipped, logged at Warn with how late it was and how many times were dropped, and the next occurrence is the first at or after the clock's reading. A "9:00 report" that starts at 9:40 is a different event, and the framework cannot tell whether it is still wanted; the application that wants a late run can run an `Every` with a short interval beside it. The grace is one constant and not an option, the same one for every job.
- **A clock that goes back never repeats an occurrence that was run.** When the timer fires and the clock reads earlier than the occurrence it was set for (the host's time was set back), the job logs it at Warn and waits for the clock to reach that occurrence; the schedule follows the clock as the app reads it. An occurrence that was run is never run again: setting the clock back an hour does not run the last hour again, because the schedule only ever moves to the next time after the one it is waiting for, and each occurrence is named by its due instant.
- **`ScheduledAt(ctx)` is the occurrence a run belongs to.** It is the schedule's instant (UTC), not the clock's: a run that starts 40 ms late, or 50 s late within the grace, has the `ScheduledAt` its due time says. It is the value to key an idempotent write on ("the report for this occurrence"), which is how a job is made safe to run twice. It is the one new function besides `Cron` and the lock, and is the zero time on a context that is not a job's.
- **A job is stopped with the app: the context is cancelled and `Stop` waits.** The Service's life is cancelled (cause `ErrServerClosed`) just before `Stop`, the timer is stopped, no occurrence starts, and `Stop` waits for a run in progress, bounded as every function of a Service is (`Shutdown`'s context, `WithServiceTimeout` under `Close`, [ADR 0029](0029-shutdown-drains-and-then-closes.md), [ADR 0079](0079-services-start-after-the-app-binds-and-stop-in-reverse-around-shutdown.md)): one that ignores its context is abandoned and logged, as a worker is. Register the job after what it uses, and it stops before it.

**The job lock.**

- **`JobLock` is a one-method interface, and a claim is of an occurrence.** `Claim(ctx, key string, ttl time.Duration) (bool, error)`. `CronOptions{Lock}` makes each occurrence be claimed before it runs, with the key `name@<due in Unix seconds>`, so two instances racing for one minute boundary ask for the same key, one gets `true` and runs, the other gets `false` and logs at Debug that another instance has it. The key names the occurrence and not only the job because a lock taken for the length of the run and released at its end lets an instance whose clock is 50 ms behind take it again after the first has finished, which is the double run the lock exists to prevent; a claim that names the occurrence and is held for its ttl cannot be taken twice. The ttl the framework passes is an hour: far more than the lateness any instance can have (a run starts within a minute of its due time or is skipped) plus any clock skew that leaves a cluster working, and short enough that a store holds an hour of keys. It is not an option: one constant is one thing less to get wrong, and a deployment whose instances disagree on the time by an hour has a larger problem.
- **A claim is not a lease, and the interface says so.** A claim says which instance starts an occurrence, not which is still running it, and nothing is released: the lock has no release, no renewal and no fencing token, so **there is no lock that can expire in the middle of a run**, and the questions that follow from one (does the job notice, who runs next, what does the first one write after it lost) have no place. What a claim cannot do is the contract of this ADR: **it is at most one run for each occurrence and not exactly one.** An instance that claims an occurrence and dies before it runs, or before it finishes, loses it (the next occurrence is another claim); a store that errors skips the occurrence on every instance; and a job that outlasts the time to its next occurrence can overlap itself across instances, because the next occurrence is a different key (on one instance it is skipped, as above). **When exactly once matters, make the job safe to run twice**, and use `ScheduledAt(ctx)` as its idempotency key (an `INSERT ... ON CONFLICT DO NOTHING` of the occurrence, a row lock on it); when a missed run is worse than a double one, give no lock and make it idempotent, which is the same job. The job that cannot be both has its own database lock, taken for the run, which the framework cannot hold for it without a lease and a way to tell the job it lost it.
- **A store that fails skips the occurrence and never runs it unlocked.** `Claim` returns `(true, err)` or `(false, err)` the same way: an error is "not claimed". The job logs at Error (`bites: job skipped: the lock store failed, so this occurrence is not run here`, with `job`, `due`, `key` and `err`), a panic in `Claim` is recovered and handled the same way, and a `Claim` that does not answer in ten seconds, or when the app stops, is cancelled through its `ctx` and skipped (the stop is logged at Warn, not Error). The schedule goes on: the next occurrence asks again, so a store that comes back resumes the job. A job with a lock that cannot reach it does nothing, loudly, which is the safe failure for a job that must not run twice; the application that prefers a double run to a missed one gives no lock.
- **`JobLock` is implemented outside the core and the core ships the in-memory one.** `bites.NewMemoryJobLock()` keeps the claims of one process, judged on `bites.Now(ctx)` so a test moves them with the app's clock, frees the expired ones as it goes, and is what a test of two instances racing shares between two Apps. A Redis implementation is `SET key 1 NX PX ttl`, and a Postgres one an insert of the key with an expiry that ignores a live row; each is a module, and each is held to the interface by the suite below ([ADR 0070](0070-optional-features-are-modules-under-modules-each-with-its-own-go-mod.md), [ADR 0086](0086-a-store-is-held-to-its-interface-by-a-conformance-suite-in-bitetest.md)). The roadmap's Redis and Postgres modules gain this interface; none is written here.
- **`bitetest.TestJobLock(t, newLock)` holds an implementation to its doc comment**, edited into [ADR 0086](0086-a-store-is-held-to-its-interface-by-a-conformance-suite-in-bitetest.md) in place: a free key is claimed, a held key is refused with `(false, nil)`, a claim holds until its ttl has passed and no longer (judged on the app's clock, so a store that reads its own fails at once), nothing releases it, each claim has the ttl it was made with, keys never share a claim (case, a trailing space), any text is a key (Unicode, 200 bytes, punctuation), a done context claims nothing and returns its error, and eight callers of one key never both win, over 60 rounds.

**Logs.** Nothing happens in silence ([principle 2](0077-four-principles-in-the-order-they-win.md)): `bites: job scheduled` at Info when the service starts, with `job`, `spec`, `zone`, the `next` time in that zone and `lock` (`none` or `set`); Warn for a run skipped because the last is still going, one skipped because its time passed in a pause or a jump (with `late`, `grace` and `dropped`), a clock that went back, and a job that failed; Error for a panic and for a store that failed; Debug for an occurrence another instance claimed (once a minute on each of the other instances is not what an operator reads by default, and it is there for the one who is looking).

**Refusals** (rows of `refusal_test.go`; every message ends with `registered at <file:line>`, and the spec is quoted whole):

- `bites.Cron: the name is empty or has a space, a quote or a control character: give the word the log and the errors call this job by, such as "nightly-report"`, and `bites.Cron("report"): fn is nil: give the function called at each time of the schedule`.
- `bites.Cron("report"): the time zone is nil: give the place the times are read in, such as time.UTC or the result of time.LoadLocation("Asia/Jakarta"); a zone is never assumed`, and for `time.Local`: `the time zone is time.Local, the machine's own: two machines of one app would run the job at different times; name the place, such as time.LoadLocation("Asia/Jakarta"), or give time.UTC`.
- `bites.Cron("report"): spec "0 25 * * *" is not a schedule: hour "25": 25 is outside 0-23`, and the same form, naming the field, for a spec that is empty, with four or six fields (six says seconds are not supported and what to use), a number outside its field, a step of zero, `5/15` (says `5-59/15`), a range that runs backwards (says to write two), a name that is not three letters of a month or a day, `?`, `L`, `W` and `#`, `@every` (says `bites.Every`), `@reboot`, and a shortcut that is not one (lists them).
- `bites.Cron("report"): spec "0 0 31 2 *" is not a schedule: it never matches a date: day 31 is not in month 2, so no day of any year qualifies; check the day-of-month and month fields`.
- `bites.Cron("report"): 2 options values were given; give one CronOptions`.

**What it costs** ([ADR 0003](0003-the-trade-budget.md)). None of the four axes moves, and `TestARouteBesideACronKeepsTheRequestAllocationsAtTwo` measures it: 2 allocations for the typed JSON POST beside a Cron with a lock. A Cron is a timer and a small struct on the Service's goroutine side, and a run is one goroutine and one `context.WithValue` for each occurrence (a minute apart at the closest), off the request path; finding the next time is a loop over months, days, hours and minutes that returns at the first match, plus a probe of the zone's offset once a day of the distance to it for a rate (a handful of probes, a few hundred for a spec that looks four years ahead), and none of it runs on a request. The memory is the lock's: one entry for each claim inside its hour.

**Scenarios it was put against.**

- _Two instances racing for one minute boundary_ (`TestTwoInstancesRacingForTheSameMinuteRunItOnceBetweenThem`): both clocks reach 00:01 at once, on two goroutines, 30 minutes running; each minute the two ran the job once between them, never twice, never none. _An instance whose clock is 20 ms behind_ (`TestAnInstanceWhoseClockIsBehindDoesNotRunAnOccurrenceTheOtherHasFinished`): the first ran and finished, the second arrives after and is refused, because the claim outlives the run. A lock held for the run and released after would fail this test, which is why it is not the design.
- _The clock jumps backwards_ (`TestACronJobNeverRepeatsATimeWhenTheClockIsSetBack`): the host's clock is set back half an hour as the next timer fires; the job logs it, re-arms for the time on the clock as it reads, and runs nothing again. _The clock jumps forward, or the process is paused_ (`TestACronTimerThatFiresMinutesAfterItsTimeBecauseTheProcessWasPausedSkipsTheRunAndNeverBursts`): the timer fires 40 minutes late, the time is skipped with `late=40m30s` and `dropped=41`, nothing runs at once, and the schedule goes on one run at a time from the next time on the clock.
- _The lock store errors, panics or hangs_ (`TestACronJobWhoseLockStoreFailsSkipsTheOccurrenceLogsItAndNeverRunsUnlocked`, `TestACronJobWhoseLockStoreHangsIsSkippedWhenTheAppStops`): the occurrence is skipped and logged and `fn` never runs, including when the store answers `(true, err)`; when it recovers the next occurrence runs.
- _The night the clocks go forward and the night they go back_ (the daylight-saving tests above, and `TestACronJobAtATimeSkippedByDaylightSavingRunsOnceAtTheInstantAfterTheGap` through a Service on a fake clock): a daily 02:30 job runs once at 03:00 and once at its first 01:30, an hourly rate runs through the repeated hour twice and skips the nonexistent one.
- _A job that outlasts its schedule_ (`TestACronRunThatIsStillGoingWhenTheNextIsDueIsSkippedAndLoggedNeverOverlapped`) and _a shutdown in the middle of a run_ (`TestAShutdownWhileACronRunIsGoingCancelsItsContextAndWaitsForItToReturn`).

**What it fails at.**

- **It is at most once, not exactly once.** An instance that claims and then crashes loses the occurrence, and a store outage skips it on every instance. Nothing in a lock-and-skip design can make both "never twice" and "never zero" true, and the ADR states which one it chose and what makes the other the job's own.
- **A job longer than the gap to its next occurrence can overlap itself across instances.** One instance never overlaps itself; two instances claim two different keys. A lease with renewal would close this at the cost of an interface that has a release, a renewal, a way to tell the job it lost the lease and a fencing token for what the job writes; none of that is built, and the job that cannot overlap takes its own lock.
- **A pause of more than a minute loses the occurrence it spans**, by choice (above), and the grace is not tunable.
- **The daylight-saving search assumes a zone changes its offset at most once between two probes a day apart.** True of every zone in the current tz database; a zone that changed twice in 24 hours (none does today) would be stepped over, and the next occurrence found at a wrong offset until the next probe.
- **A spec read in a zone whose offset has a fraction of a minute** (some zones before 1900) is not looked at: the schedule counts whole minutes.
- **Seconds are not available**, and the rule that a day with both fields restricted matches either is the surprising one in cron; it is the one every cron has, and a test pins it.

What was rejected, with the reason:

- **A lock held for the run with a release function** (`Acquire(ctx, name, ttl) (release, error)`, the shape that first comes to mind). Rejected for three reasons that came out of the stress tests. An instance whose clock is a few milliseconds behind takes the lock again after the first has released it, so the occurrence runs twice; the cure is to hold the name until the ttl, at which point release does nothing. A ttl shorter than the run lets the lock expire in the middle of it, and then the interface must say how a job learns it lost the lock and what it may still write, which is a lease protocol (renewal, fencing) the framework would have to ship and every store to implement. And three methods are more for an agent writing a Redis module to get wrong than one. A claim of the occurrence is the smaller thing and has no mid-run expiry to handle.
- **`@every <duration>` in the spec.** Rejected: it is `Every` spelled a second way, and as a cron entry it is relative to when each instance started, so the lock has nothing to line up.
- **The zone inside the spec (`CRON_TZ=Asia/Jakarta 0 9 * * *`)** and **a default zone** (UTC, or the machine's). The first moves a required fact into a string that is checked at Registration and not by the compiler, and its name is loaded by the framework on a machine that may have no zone files, where the application can see the error; the second is the silent default the principles refuse, and the machine's is the one that differs between the laptop and the container.
- **A seconds field and `AtStart`.** Rejected: a schedule finer than a minute is an interval (`Every`); a run at start is what `Every` with `AtStart` and a `Worker` already say, and a cron has no "now" to run for.
- **The pure rule for every spec (run the instants the clock shows, so a time that does not exist is not run and one that occurs twice runs twice).** The simplest rule, and one `next` could have been written with; it skips a daily job one night a year without a word and runs it twice another, which is the bug the framework exists to remove for an application that wrote `30 2 * * *`. It stays the rule for a rate, where it is what the spec means.
- **Running the missed occurrence late, once, after a pause.** Rejected for the reason above: the framework cannot know whether a late run is still wanted. Skipped and logged says what happened; the application that wants it adds an `Every`.
- **A ttl in `CronOptions`.** Rejected: nothing in a claim of an occurrence needs a choice, and a choice here is a way to lose or double a run.
- **A `Cron` that is a module.** Rejected: the parser is standard-library only and about 350 lines, and `Every` and `Worker` live in the core ([ADR 0070](0070-optional-features-are-modules-under-modules-each-with-its-own-go-mod.md)); the stores that need a dependency are the modules.
