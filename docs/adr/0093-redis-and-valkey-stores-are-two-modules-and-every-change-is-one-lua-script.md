# Redis and Valkey stores are two modules, and every change is one Lua script

[ADR 0085](0085-a-postgres-rate-limit-store-is-a-module.md) and [ADR 0082](0082-a-postgres-session-store-is-a-module.md) gave an application that runs Postgres a shared `RateLimitStore` and an `OwnerSessionStore`. An application whose instances share Redis or Valkey rather than Postgres (the cache and the queue of many deployments, and what Fiber's storage, httprate and Gin's and Hertz's sessions are written against) had to write both: the two seams were built with a Redis store in mind (the doc comments of [`RateLimitStore`](0055-rate-limiting-is-a-token-bucket-per-key-with-a-bounded-store.md) and [`OwnerSessionStore`](0056-a-session-is-sealed-in-a-cookie-and-changed-by-returning-its-cookie.md) name it) and [ADR 0086](0086-a-store-is-held-to-its-interface-by-a-conformance-suite-in-bitetest.md) built the suite a Redis store must pass. Decided on 2026-11-17 and built.

**Decision.**

- **Two modules, named as the Postgres pair is: `modules/redisratelimit` and `modules/redissession`**, each with its own `go.mod` ([ADR 0006](0006-no-third-party-dependency-in-the-core.md), [ADR 0070](0070-optional-features-are-modules-under-modules-each-with-its-own-go-mod.md)); the core changes nothing. A module is named for the backend and the feature (`pgsession`, `pgratelimit`, `pgnotify`), so an agent that knows one finds the others by the same rule, and the Redis `Broker` of the roadmap will be `redisnotify` or `redisbroker` beside them without a rename. `redisratelimit.New(Options) *Store` implements `bites.RateLimitStore`; `redissession.New(Options) *Store` implements `bites.OwnerSessionStore`. Both `Options` have `Client` (required, never closed) and `Prefix`; the rate limit one has `Name` as `pgratelimit`'s does. **Neither has a Service**, a `Sweep`, a `Schema` or a `CreateTable`: Redis deletes a key whose TTL has ended, so there is nothing to sweep and nothing to create, and the one way to start is `New`.
- **The client is go-redis v9 (`github.com/redis/go-redis/v9`), and `Options.Client` is a `redis.UniversalClient`.** It is the Go client that the Redis documentation points to, so it is the one an application running Redis most likely holds already and an agent writes `redis.NewClient(&redis.Options{Addr: ...})` for without being told ([principle 1](0077-four-principles-in-the-order-they-win.md)). One interface covers a single server (Redis or Valkey), Sentinel (`redis.NewFailoverClient`), `*redis.ClusterClient` and `*redis.Ring`, so the module takes what the application has and picks nothing for it. Its `Script` sends `EVALSHA` and falls back to `EVAL` when the server answers `NOSCRIPT`, which is what makes a script usable without a load step. It adds three small dependencies (`xxhash`, `go.uber.org/atomic`, `golang.org/x/sys`) to the module and none to the core. **Valkey** speaks the same protocol, `EVAL` and the same commands, and the two modules' tests pass against Valkey 8 as against Redis 7 (the numbers below). The module takes no `valkey-go` client: an application on Valkey gives go-redis its address, which is one way to do it.
- **Every change is one Lua script, so it is one round trip and atomic.** Redis runs a script without running any other command, so a read, a decision and a write are one step for every instance that shares the server, with no `WATCH`, no lock and no retry. Each script names every key it touches in `KEYS`, so it runs on a cluster. A script is sent by its SHA-1 and the whole text only when the server has forgotten it (a restart, `SCRIPT FLUSH`; tested), which is a second command once.
- **Time is the application's, and Lua's numbers are doubles, so time is kept in microseconds.** A Lua number holds an integer exactly up to 2^53. A Unix time in nanoseconds (1.7e18, what `pgratelimit` keeps in a `bigint`) is not exact in it, and a time in microseconds (1.7e15) is. So the stores keep microseconds: a bucket's time, a session's expiry, the arguments and the numbers written back (formatted with `%.0f`, since Lua prints a double with 14 digits). The price is stated as three refusals of `Take`: an interval under one microsecond, a bucket longer than 2^51 microseconds (about 71 years), and a `now` outside 1970 to 2112; an interval that is not a whole number of microseconds is rounded to one, which moves a limit by less than a millionth of its interval.

**`redisratelimit`: one key a bucket, GCRA in one script.**

- **The algorithm is GCRA with one number a key, the same as the in-memory store and `pgratelimit`** ([ADR 0085](0085-a-postgres-rate-limit-store-is-a-module.md)): the key holds `tat`, the time the bucket is next full. The script reads it, takes the later of it and now, adds one interval, and writes it back only when the result is at most `burst` intervals ahead of now. It returns whether the request was spent and the time, and Go computes `Remaining`, `RetryAfter` and `Reset` as `pgratelimit` does, so the stores answer alike and pass the same suite.
- **A refused request writes nothing**, so a client that keeps trying neither pushes its own retry time away nor refreshes the key's TTL, and a flood of refusals costs reads.
- **The key is the prefix, a colon and the base64url of a SHA-256** of the Name's length, the Name and the key, so a dump of the keyspace or a `KEYS *` shows no email or address and two limiters that share a Redis do not share a bucket. The hash does not make a small key space unguessable (an email can be tried against a list), as for `pgratelimit`, and an HMAC with a secret is rejected for the reason given there. **Buckets are spread over a cluster's shards**, one key each, since no script touches two.
- **Expiry is a TTL of the time until the bucket is full again plus one minute** (`SET ... PX`): Redis deletes a bucket that has been full for a minute, a full bucket is what a new key gets ([ADR 0055](0055-rate-limiting-is-a-token-bucket-per-key-with-a-bounded-store.md)), and the minute is the grace that keeps that true when the instance that wrote the key runs behind the one that reads it by less than a minute, as `pgratelimit`'s `SweepGrace` does. The table is bounded in practice by the keys active in the last bucket length and a minute, and by what clients can make; the application's own address limit in memory in front is what bounds a client that rotates a key it controls.
- **The clock is `Take`'s `now`, never Redis's `TIME`.** For the reasons of [ADR 0085](0085-a-postgres-rate-limit-store-is-a-module.md): the suite and `bitetest.Clock` move `now`, and a limiter measures on the application's clock. Instances whose clocks differ by `s` differ in their limit by at most `s` of bucket, not accumulating; keep them within a second with NTP.

**`redissession`: a hash a session, a sorted set an owner.**

- **A session is a hash `{prefix}:id:<sha256 of the id>`** with three fields: `e` the expiry in microseconds, `o` the SHA-256 of the owner (empty for none), and `d` the data, the framework's own bytes that the store never reads inside. The id is stored only as its hash for the reason of [ADR 0082](0082-a-postgres-session-store-is-a-module.md), and the owner too, which costs one hash and keeps an owner (an email, in some applications) out of a dump of the keyspace. `Load` is one `HMGET` of `e` and `d` and judges `e > bites.Now(ctx)` in Go.
- **Expiry is judged on the application's clock, and the TTL only frees the space.** The expiry is kept in the hash and compared with `bites.Now(ctx)`, the clock that computed it and that checks the one sealed in the cookie, so a session on a test clock (the suite's fake clock reads 2026) and a server whose clock drifts do not disagree with the cookie: [ADR 0086](0086-a-store-is-held-to-its-interface-by-a-conformance-suite-in-bitetest.md) says a Redis store computes a TTL as `expires` minus `bites.Now(ctx)`, and this does, rounded up to a millisecond, so Redis deletes the key when its time ends and nothing sweeps. A `Save` with an expiry that is not after now keeps nothing and deletes what the id had.
- **The owner's index is a sorted set `{prefix}:owner:<sha256 of the owner>`** of the sessions' hashes, scored by their expiry, and `SaveOwned` is one script that writes the hash and adds the session to the set. The set is given a TTL at least as long as its longest session, and is trimmed of members whose score is past (`ZREMRANGEBYSCORE`) on every save of that owner, so it holds the live sessions and not every login the owner ever made. **`DeleteOwner` reads the set and ends the sessions in scripts of 500 keys**, counting only a session whose own `o` is this owner and that is not `keep`. That check is what makes the set allowed to be stale: a session that changed owner (`SaveOwned` of the same id for another owner) or was deleted stays in the old set until it is trimmed or `DeleteOwner` passes it, and is never counted or ended there, so `Delete` is one `DEL` and a change of owner is one script. A script that had to know the old owner would read a key it was not given, which breaks on a cluster. `DeleteOwner` counts the sessions it deleted that Redis had not yet deleted for age, as `pgsession` counts unswept rows.
- **A slide is `Touch`, two round trips.** `Touch` has an id and no owner, and the owner's set is a key the script must be given, so `Touch` reads the session's `o` and then runs a script that moves the expiry, the TTL and the score in the set **only if `o` is still what was read**; when another call changed the owner in between, the script returns -1 and `Touch` reads again (three times, then an error that says so, tested with a hook that changes the owner between the two). It never creates a key: a session that is gone, deleted by `RevokeOwner` or expired on the application's clock is `(false, nil)` with nothing written, which is the race of a slide against "sign out everywhere" that the suite holds. **Moving the score matters for revocation:** a touched session whose score stayed at its first expiry would be trimmed from its owner's set by the next save of that owner while still alive, and `RevokeOwner` would miss it, a stolen cookie that survives "sign out everywhere" (`TestATouchedSessionIsNotTrimmedFromItsOwnersSetAndSoIsRevoked`).
- **Every key of a Store starts with `{prefix}`, a Redis Cluster hash tag**, so a session and its owner's set are on one shard and the scripts that name both run on a cluster (checked against a Redis Cluster node that owns every slot, where a script naming two slots is refused; not against a cluster of several nodes). The cost is that one Store lives on one shard: sessions do not spread over a cluster. A braced prefix is refused at `New`, since the Store adds the braces; an application that needs more than one shard of sessions gives different Stores different prefixes.

**Refusals** (rows of the two modules' `_test.go`, each ending `registered at <file:line>`; the references list them):

- `redisratelimit.New: Client is nil: give the application's client, such as redis.NewClient(&redis.Options{Addr: "localhost:6379"})`, and the same for `redissession.New`.
- `redissession.New: Prefix "<p>" contains a brace: the Store puts the prefix inside braces, a Redis Cluster hash tag, so give a prefix such as "<p without braces>" without '{' or '}', or leave it empty for "bites:session"`.
- `Take` errors that say what to change: a burst under one, an interval that is not positive or is under 1µs, a bucket too long for the exact range, a `now` outside the years the range holds.
- Not caught before the first request: **a Redis that evicts** (`maxmemory-policy allkeys-*`, or `volatile-*` under memory pressure) deletes buckets and sessions before their TTL, which resets limits and signs users out, so give the server `noeviction` or room, and the references say so; **a Redis older than 4.0** (`HSET` with several fields); two limiters on one prefix and one `Name`, and two `Sessions` types on one prefix, which share buckets and owners (give each its own); instances of one limiter given different Names.

**What it costs** ([ADR 0003](0003-the-trade-budget.md)). Core: none; no file of it changes, so allocations per request and memory per idle connection do not move. Module: one round trip to Redis for each limited request, and for each `Load`, `Save`, `SaveOwned`, `Delete` and `DeleteOwner` of up to 500 sessions, and two for a `Touch` (one when the session is gone); a request that does not read the Session does not touch Redis. Measured on the Ryzen 7 9700X with Redis 7 in Docker over loopback, `BenchmarkTake` (three runs, 2 s each): **about 21 to 31 µs a `Take`** for a new key from one caller (25.1, 20.8 and 31.3 µs), **17.7 to 19.6 µs** for a refused request, and **about 5.3 µs a `Take`** when 16 goroutines take the one key (5.2 to 5.5 µs), Redis running scripts one at a time; the `pgratelimit` figures on the same machine are 26, 22 and 7 µs, and a loopback round trip is a floor that a network adds to. Memory, from `MEMORY USAGE`: **104 bytes a bucket**, **216 bytes for a session** whose data is 21 bytes, and 184 bytes for the owner's set holding its first session. Per store, no goroutine, since nothing is swept. No number of [ADR 0003](0003-the-trade-budget.md) is raised.

**Scenarios it was put against.**

- _Three instances behind a balancer, a limit of 5 a minute per email_: every instance takes from the same key, so the application allows 5 (`TestARateLimiterOnTwoInstancesLimitsOnceNotTwice`); forty rounds of eight concurrent takers over two clients on a burst of 3 are allowed exactly 3 each, and the suite's concurrent subtests hold it for one store.
- _A hostile client_ guessing a password from a thousand addresses: each address is a key, the limit per email is one key all of them contend on, and Redis serialises them at about 5 µs each.
- _A flood of refused requests on one key_: each is a script that reads and writes nothing, so no key is rewritten and no TTL refreshed.
- _A dump of the keyspace_ (an `RDB` file, a `MONITOR` log, `KEYS *`): hashes, expiries and times; for a session, the data in the clear and the owner as a hash. A session that holds a secret should not hold it in the data, as for `pgsession`.
- _A forged or stolen cookie_: as [ADR 0082](0082-a-postgres-session-store-is-a-module.md); every value passed to Redis is an argument and the key text is built from hashes and the prefix, so a client cannot choose a key.
- _A revoke racing a save_ (a refresh of a sliding session included): as [ADR 0082](0082-a-postgres-session-store-is-a-module.md) says, `DeleteOwner` reads the set and a `SaveOwned` that lands after the read is not seen, and a request that loaded before the revoke and saves after puts the session back; the application's Provider refuses a disabled User on every request and the order is disable, revoke, close the sockets. A **slide** racing a revoke cannot bring a session back (`Touch` only writes a live hash).
- _Redis restarts with no persistence, or fails over to a replica that had not received the last writes_: the buckets are empty (every limit resets once, as for an unlogged table) and the sessions written since the replica's last sync are gone, which signs those users out. A deployment that cannot accept that turns on persistence (AOF) and accepts its fsync policy; the module does not choose it. **A client that reads from replicas** (`ReadOnly` or `RouteByLatency` on a cluster, `ReplicaOnly`) would `Load` a session a revoke has already ended: do not configure it for the client the sessions use.
- _Redis is down_: every limited request and every request that reads a session is a 500 until it is back ([ADR 0055](0055-rate-limiting-is-a-token-bucket-per-key-with-a-bounded-store.md), [ADR 0056](0056-a-session-is-sealed-in-a-cookie-and-changed-by-returning-its-cookie.md)); an application that would rather serve wraps the store.
- _The script cache is lost_ (`SCRIPT FLUSH`, a restart, a failover to a replica that never ran it): the next call gets `NOSCRIPT`, sends the script whole and goes on (`TestTheScriptIsSentAgainWhenRedisForgotIt`).
- _An owner with 1234 sessions_: `DeleteOwner` ends them in three scripts of at most 500 and keeps the one it was told to keep (`TestAnOwnerWithMoreSessionsThanOneBatchIsEndedWhole`).
- _An instance's clock 30 s ahead_: as [ADR 0085](0085-a-postgres-rate-limit-store-is-a-module.md); and a session's expiry is compared on the clock of the instance that loads it, so a skew moves a session's end by the skew, as for the sealed expiry of the cookie.

**What it fails at.**

- **A round trip a limited request and a session request**, which an in-memory limit and a sealed-cookie session do not pay; `Touch` is two, and happens only when a session slides.
- **A hot bucket is one key**, so takes on it serialise on Redis's single thread, about 5 µs each here; a limit that busy belongs in memory.
- **One Store of sessions is one shard of a cluster**, and a cluster that is not one node was not run.
- **Eviction and failover lose state** (above), and a limit or a session lost is a limit reset or a user signed out, not an error.
- **Time in microseconds**: an interval under 1µs and a bucket over 71 years are refused, and a `now` after 2112.
- **A stale owner's set** holds a member until it is trimmed or `DeleteOwner` passes it; an owner who signs in at a rate of one a second for a week and never again has 600,000 members until the set's TTL ends, which is its longest session. The cap is the sessions' lifetime, not a number the module chooses.
- **`DeleteOwner` is not atomic across batches**: a revoke of 1234 sessions is three scripts, and a session saved between them is in the set the first read did not hold.
- **Skew** and a **guessable hash for a small key space** are as for `pgratelimit`.
- **The key layout is not migrated**: a later version that changes a key or a field needs a migration the application runs; the references show what this version writes.

**Considered and what was rejected.**

- **One module `redisstore` with both stores**: one `go.mod`, one reference page and one dependency line, at the price of a name that does not follow the rule of the Postgres pair, and of a module an application that wants the rate limit alone links the session code of. The modules share no code worth a third package; the duplicated part is a dozen lines.
- **`valkey-go` or `rueidis`** (auto-pipelining and client-side caching): faster for a workload the stores do not have, since a limit or a session read is one command, and an application on Valkey would hold a client other than the one its Redis tooling uses. Revisit if an application's load asks.
- **`WATCH`/`MULTI`/`EXEC`** for a take: two or three round trips and a retry when another instance writes the key first, which is the contention the script avoids.
- **A fixed window with `INCR` and `EXPIRE`**: no arithmetic and the doubled limit at a window boundary, for the reasons [ADR 0055](0055-rate-limiting-is-a-token-bucket-per-key-with-a-bounded-store.md) and [ADR 0085](0085-a-postgres-rate-limit-store-is-a-module.md) give.
- **`redis-cell` (`CL.THROTTLE`) or Redis functions**: a Redis module the stock server and Valkey do not load, and `FUNCTION LOAD` is a step the application would run before the first request, where a script is sent by the first call that needs it.
- **`TIME` inside the script** for a clock shared by every instance: exact between instances, and the suite and `bitetest.Clock` could not move `now`, so a test of a limit would sleep ([ADR 0085](0085-a-postgres-rate-limit-store-is-a-module.md)).
- **Nanoseconds as strings with a big-integer routine in Lua**: exact for any time, at the price of arithmetic in a script that every store must get right; microseconds are exact where limits and sessions live and the three refusals say where they stop.
- **The expiry only as a TTL** (no `e` field): Redis's clock then decides, which a fake clock cannot move and a drifting server would put in disagreement with the cookie; the suite fails it at once.
- **A plain set for the owner** (`SADD`): no score to trim by, so a set of every login that was ever made, cleaned only by `DeleteOwner`; the score is what bounds it.
- **A script that finds the old owner and removes the session from its set** on a change of owner and on `Delete`: it reads a key it was not given, which Redis documents as unsafe on a cluster; the lazy check at `DeleteOwner` costs the stale member and no correctness.
- **One owner set per session type and no hash tag**: spreads sessions over a cluster, and makes `SaveOwned` a script over keys in two slots, which a cluster refuses.
- **A `Service` that sweeps** as `pgsession` has: nothing to delete, since Redis does.
- **`Prefix` without braces added by the caller**: an application would write the hash tag, or forget it and find the scripts refused on a cluster, so the Store adds it.
