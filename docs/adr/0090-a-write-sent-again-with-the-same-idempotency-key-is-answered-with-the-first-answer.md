# A write sent again with the same Idempotency-Key is answered with the first answer, from a bounded store the application can replace

`NewIdempotency(IdempotencyOptions{...})` returns an `Idempotency`, whose `Middleware()` is given to a route or a group with `Use`. A `POST` or `PATCH` that carries an `Idempotency-Key` is claimed in a store before its handler runs; the handler runs once; the answer is kept when the request did its work; and the same request sent again, because the client timed out or a webhook was redelivered, is answered with that answer and `Idempotent-Replayed: true`, and the handler does not run. Built 2026-11-17 (`idempotency.go`, `idempotency_mem.go`, `bitetest/idempotency.go`). The behaviour follows the IETF draft `draft-ietf-httpapi-idempotency-key-header` (409 for a duplicate that is still running, 422 for a key used with another request) and the practice of Stripe, which is what the client libraries of payment providers already do.

**Decision.**

- **It is a middleware that reaches the exchange behind the `Request`.** A middleware sees neither the request body nor the answer body ([ADR 0022](0022-middleware-sees-a-request-view-and-returns-a-response-value.md)), and both are what this feature needs: the body to tell a retry from a different request, and the answer to send again. It is the root package, as for `RequestID` and the `RateLimiter` ([ADR 0032](0032-four-first-party-middleware.md)), that reads them, through the chain's state the `Request` points at, so the public `Request` and `Response` gain no method and a user's middleware gains no power. The request body is read with `Exchange.ReadBody` and the route's own `MaxBody` and `BodyTimeout`, which the route now keeps (`route.maxBody`); a second `ReadBody`, the Input's, returns the same bytes, so nothing is read twice. The answer is read from the engine's pending response after `next` returns: its status, its Content-Type, its header block (`engine.Response.HeaderBlock`, a view copied before it is kept) and its body, copied. Nothing pooled reaches user code ([ADR 0008](0008-no-pooled-object-reaches-the-user.md)): the store is given copies it owns, and the replay is a fresh `Response` built with `NewResponse`, `SetBody` and `AddHeader`, so the answer still comes only from a return value ([ADR 0009](0009-the-response-comes-only-from-the-return-value.md)).
- **What is covered.** A request with the method `POST` or `PATCH` and the key header. Every other method passes through untouched: `GET`, `HEAD`, `PUT` and `DELETE` are idempotent by definition (RFC 9110 section 9.2.2). A `POST` or `PATCH` with no key passes through unprotected, unless `Required` is set, which answers 400 problem+json with `errors[0].location` `header.Idempotency-Key`; a route that takes payments sets it. There is no `Methods` option: one way to do a thing.
- **Where the key comes from.** The header `Idempotency-Key`, or `Header`. It is 1 to `MaxKeyLength` bytes (255; at most 1024) of printable ASCII with no space, quote or comma; one pair of double quotes around it, the structured-field form the draft writes, is removed, so `"k"` and `k` are one key. An empty, long or malformed key is a 400 problem+json whose error is located `header.Idempotency-Key` and whose message states the rule; a key sent on two header lines is a 400 too, since the comma is refused and no one can say which was meant. The check is a scan of the request's copy of the head: no allocation.
- **Whose key it is.** A key means something only for the client that sent it, so the store's key is a hash (SHA-256, 128 bits kept, hex) of the route's pattern, the scope and the key. The same key on two routes is two keys. The scope is `Scope(Request)`, and when it is nil it is what the request presents as credentials: the `Authorization` header and every `Cookie` header, so two clients with different tokens or sessions never share a key, and a client that does not hold the same credentials cannot read another's answer by guessing its key. The failure of the default is toward running the request again, never toward showing someone else's answer: a token that is renewed between a request and its retry is a new scope. A middleware runs before the Providers ([ADR 0048](0048-groups-and-the-order-things-run-in.md)), so the user's id is not known here; the credential stands for it, and an application whose credentials rotate (a short-lived bearer) gives `Scope` a stable value such as an API key's prefix or a tenant header. A `Scope` that returns "" gives every request one scope, for a route whose callers are not authenticated (a webhook) and whose keys are unguessable. The store sees only the hash, so it never holds a credential and a key has a fixed length whatever the client sent.
- **Same request or not.** The fingerprint is a SHA-256 of the method, the path and the query as sent, and the body as received (compressed bytes included), each length-prefixed so that no boundary can be moved. A key sent again with another fingerprint is **422** problem+json, which says to send a new key for a different request, and the handler does not run. Headers are not part of it: a client library may add a header between attempts.
- **A duplicate while the first runs is 409 with `Retry-After: 1`, not a wait.** The draft says 409, and waiting would need the store to tell every instance when a claim ends, which an interface that Redis and Postgres implement cannot promise; polling would hold the connection and the goroutine for as long as the first request, and the client already has a retry loop. The claim lasts `InFlight` (a minute by default, at most `TTL`), so a crashed instance never blocks a key for the day.
- **What is kept, and what is not.** The answer of a request that did its work: a 2xx or a 3xx. Not kept, and the claim released so a retry runs: a 4xx (the request was refused and nothing was done: a 400 for a field, a 401, a 403, a 429 from a Provider, a 404, a 409 or a 422 from the handler), a 5xx, a panic (the claim is released by a deferred call as the panic goes through), a stream, and an answer the chain did not produce. A 401 that was kept would turn away the same request sent again with a good token; a 5xx that was kept would be the draft's "MAY", and it is refused because the handler may have failed before doing anything. What the rule fails at is below. The release uses a context that is not cancelled with the request, as does the keeping: the client that timed out and went away is exactly the one whose retry must find the answer of the work that finished.
- **An answer that is too large is not kept, and the work is still not run twice.** `MaxAnswer` (64 KiB) bounds a body. Over it, the store keeps only that the request was handled (`IdempotencyAnswer.TooLarge`), a duplicate gets **409** whose message says the request was handled and its answer was too large to keep, and the application reads the resource it changed; a line at Warn names the route, the size and the limit. Running the work again, which keeping nothing would do, is what the middleware exists to prevent.
- **The store is an interface so Redis and Postgres can implement it.** `IdempotencyStore` has three methods: `Claim(ctx, key, fingerprint, now, inFlight)` atomically records a claim or says what holds the key (`Claimed`, `Running` with the claim's fingerprint, `Done` with the first request's fingerprint and the `IdempotencyAnswer`), `Complete(ctx, key, fingerprint, answer, now, ttl)` keeps an answer whether or not the claim is still the caller's, and `Release(ctx, key)` frees a claim and nothing else. It decides with the `now` it is given, which is the app's clock ([ADR 0027](0027-an-in-memory-entry-point-runs-the-engine-path.md)), so a test moves `bitetest.Clock`. A store that cannot take a new key returns `ErrIdempotencyStoreFull`, which is a 503 with `Retry-After`; any other error is the answer, a 500, and the handler does not run: the middleware fails closed, since running without the claim is the double charge. `IdempotencyAnswer` is plain exported fields so a module can store it as JSON. It is held by `bitetest.TestIdempotencyStore` ([ADR 0086](0086-a-store-is-held-to-its-interface-by-a-conformance-suite-in-bitetest.md)): fifteen subtests, one for each promise of the doc comment, among them that of eight callers of one key exactly one is claimed, in each of 60 rounds.
- **The in-memory store is bounded and ships in the core.** One map and one list of the entries that hold an answer, oldest completion first, under one lock held for a map operation. `MaxKeys` (10,000) and `MaxBytes` (16 MiB, headers and bodies counted, at least twice `MaxAnswer`) bound it. To make room it drops answers, oldest first; **a claim is never dropped**, because dropping a claim would let a duplicate run beside the request it duplicates, and a store holding nothing but running requests refuses a new key with `ErrIdempotencyStoreFull` (a claim whose time passed is no one's and is swept first). Memory is 559 B a key for a 200 B body and two headers, measured as heap after 10,000 kept answers (`TestTheMemoryIdempotencyStoreHoldsAnAnswerOfAFewHundredBytesInUnderAKilobyte`), where the store's own count is 538 B, so the bound on bytes holds to about 4%; it is per instance. When an answer is dropped before its time, the middleware says so, at most every ten seconds, at Warn, with the number dropped, since a retry of one of those keys runs again.
- **A replay says so.** The answer carries `Idempotent-Replayed: true` and the access log, which reads the attributes the middleware added, has `idempotency=replayed`; a duplicate refused has `in_flight`, `mismatch` or `too_large`. The replay is the first answer whole: status, Content-Type, the headers of the handler and of the middleware inside `Idempotency` (a `Location`, a `Set-Cookie`), and the body as the handler produced it, compressed or not by this request's own negotiation. The middleware outside it (`RequestID`, `CORS`, a rate limiter) decorates the replay as it does any answer, which is why `Idempotency` goes inside them: a replay then carries this request's id and counts against the limit.

**What it costs** ([ADR 0003](0003-the-trade-budget.md)). Allocations: a route without the middleware is unchanged (2, the same row), and a route with it and a request with no key is **2** too (`TestATypedJSONPOSTBehindIdempotencyCostsWhatTheTableOfADR0089Says`). A request with a key pays for the two hashes, their hex, the copy of the answer and the store: **19 to 21** for a replay and **22** for the first request of a key on the typed POST (the test holds 22 and 24); a handler's answer of a few hundred bytes is copied once. These are not budgeted, since a request that carries a key is a write the client will repeat, not the reference workload's read. Memory per idle connection: none. Throughput and p99 are not measured yet; they wait for the serial run (one lock on a map for a request that carries a key, and a SHA-256 of the whole body, whose cost grows with the body up to `MaxBody`, a claim until it is measured).

**Refusals** (rows of `refusal_test.go`). At construction: a `Header` that is not a token; a `MaxKeyLength` negative or over 1024; a `TTL` under a second; an `InFlight` under a second or over the `TTL`; a negative `MaxAnswer`, `MaxKeys` or `MaxBytes`; `MaxKeys` or `MaxBytes` given with a `Store`; a `MaxBytes` under twice `MaxAnswer`. At Registration: `Idempotency` given to `App.Use`, which has no route to keep an answer for and no body limit to read with, and on a route that returns a `File`, a `Stream`, `SSE` or `Events` (the answer is written after the middleware has returned) or whose body is an `Upload`, a multipart form or a `BodyReader` (read part by part, never whole), recognised by its code as `CORS` and the `RateLimiter` are ([ADR 0069](0069-the-api-document-states-what-a-routes-providers-and-middleware-ask-and-answer-and-a-route-can-be-left-out.md)). **What cannot be caught before the first request:** an `Idempotency` wrapped in the application's own middleware (not recognised, so its route is not checked), a `Scope` that gives every client the same value, a handler that does part of its work and then returns a 4xx (the retry runs it again), and a store whose time to live is shorter than the `TTL` the application meant.

**Scenarios it was put against.**

- _A payment retried after a timeout_: the client times out at 10 s and sends the same key again. The first request's context is cancelled when the client leaves ([ADR 0016](0016-the-handler-context-is-cancelled-on-disconnect.md)); a handler that honours it returns an error, nothing is kept, and the retry runs; one that finishes is kept all the same (`TestAnAnswerIsKeptWhenTheClientHasGoneAwayBeforeItWasReady`) and the retry gets 409 until it has, then the answer. A retry that arrives while the first still runs is never a second charge.
- _A hostile client sending a new key every request_: the store holds `MaxKeys` entries and `MaxBytes` bytes and never more (`TestAClientFloodingUniqueKeysNeverGrowsTheMemoryIdempotencyStorePastItsBounds`, 100,000 keys through a store of 1,000); it keeps the newest and drops the oldest answers. What it can do is push another client's old answer out, after which that client's retry runs again; the log line says it happened. The answer to a client that floods is a rate limit in front ([ADR 0055](0055-rate-limiting-is-a-token-bucket-per-key-with-a-bounded-store.md)), since each unique key is also a handler that ran. If it floods with claims that never finish the store refuses new keys with a 503 and Retry-After rather than drop a claim.
- _An unauthenticated client_: it can make the route read a body of up to `MaxBody` before its Provider refuses it, because the body is read to fingerprint the request, and a Provider normally answers first; the route's `MaxBody` and `BodyTimeout` bound it. Its 401 is not kept and its claim is released, and a key in its own scope is no one else's.
- _Two instances behind a balancer_: the in-memory store is per instance, so a retry that lands on the other instance runs the handler again. This is the case the interface is for: a shared store (a Redis or Postgres module, item 1 of [`roadmap.md`](../roadmap.md)) makes the claim atomic across instances, and `bitetest.TestIdempotencyStore` is what holds it to that. The guide says so where `Store` is described.
- _A client that reuses a key for a different request_: 422, with no run. _A key stolen or guessed_: another credential is another scope.
- _A handler that panics_: the claim is released as the panic unwinds, the engine answers 500 ([ADR 0028](0028-panics-are-recovered-by-the-engine.md)), and the retry is not a 409.
- _A webhook delivered twice_: the provider's event id is the key, the route has `Scope` returning "" and `Required`, and the second delivery gets the first answer.

**What it fails at.**

- A handler that does part of its work and then answers a 4xx, or a 5xx after a partial write, runs again on the retry: the rule keeps only what is certain to have happened. A handler that must not repeat a half-done step is the application's to make safe, as it was without the middleware.
- A claim past `InFlight` is lost: a handler that runs longer than a minute (the default) may be run again by a duplicate. `InFlight` is above the longest the route can take, and a `Timeout` belongs on the route.
- The in-memory store drops answers under pressure and forgets them on restart; a retry after either runs again.
- The fingerprint ignores headers, so two requests that differ only in a header, a `Content-Type` say, are one request. The key and the body are what a client repeats.
- The body is read whole before the Providers run (above) and held for the length of the request, as any body is.
- A `Scope` that is the default changes when a client's token is renewed, so the retry runs again (it fails toward running, not toward exposing).
- A replayed answer's own `Set-Cookie` is the first one's: a session cookie kept inside it is sent again, which is what "the first answer" means, and why the scope is the credentials.
- The idempotency of the handler's effects is the handler's; this keeps the framework from running it twice for one key, not two keys from meaning the same thing.

**Considered and what was rejected.**

- **Wait for the first request and then replay, instead of 409.** One request-length of a goroutine and a connection per duplicate, a notification the store interface cannot give across instances, and polling that a client's own retry already does; the draft says 409.
- **Keeping every answer, 4xx and 5xx included** (Stripe keeps nearly all). A kept 401, 429 or 400 would turn away the corrected request that has the same key, and a kept 5xx hides that the work may not have happened. Stripe's own exception list (validation failures, conflicts) is this rule written the other way round.
- **A global scope by default.** Anyone who learned or guessed a key would read another client's answer: a leak by design. A default scope of credentials trades a rerun for that.
- **The user's id as the scope.** The Provider runs after the middleware ([ADR 0048](0048-groups-and-the-order-things-run-in.md)), so it is unknown here; moving the claim to after the Providers needs a hook inside the route, which is a second kind of middleware. `Scope` covers a stable value; this is revisited when an application needs the id.
- **A feature of the engine, as gzip and ETag are** ([ADR 0022](0022-middleware-sees-a-request-view-and-returns-a-response-value.md)). It would put a store, a clock and a policy in the engine, which the core keeps to bytes and connections. The root package already reads the exchange for `RequestID` and the rate limit's slab, so this adds one reader (`HeaderBlock`) and two fields on the route.
- **Opening the body to every middleware** so `Idempotency` could be an ordinary one: it breaks the contract the API document is built from and hands a pooled buffer to user code ([ADR 0022](0022-middleware-sees-a-request-view-and-returns-a-response-value.md), [ADR 0008](0008-no-pooled-object-reaches-the-user.md)).
- **Dropping the oldest key when the store is full, claims included** (an LRU): a dropped claim lets a duplicate run beside the original. Answers go oldest first, claims never.
- **Refusing a new key when the store is full of answers**: one client with a valid key and a loop would stop every other client's writes for a day. The price is the flood case above, said in the log.
- **Not keeping an answer over the limit, so the retry runs again**: the retry would then do the work twice, the failure the middleware prevents, for the one answer that happened to be large. The marker keeps the guarantee and loses the answer.
- **A key that is the structured-field string only, or bare only.** Clients follow the draft (`"k"`) or Stripe (`k`); accepting both as one key costs two lines.
- **A `Methods` option, and a `Keep(status)` function**: a second way to say what the rule says. `PUT` and `DELETE` need no key, and the status rule is one sentence.
- **A Redis or Postgres store in this change**: a module with its own `go.mod` ([ADR 0070](0070-optional-features-are-modules-under-modules-each-with-its-own-go-mod.md)), written against the interface and the suite when an application asks.
