# permessage-deflate is offered in its no-context-takeover mode, off by default

**`WithWebSocketCompression(WebSocketCompression{MinSize})` offers permessage-deflate (RFC 7692) to every client that asks for it, in the one mode that keeps no memory for a socket: `server_no_context_takeover` and `client_no_context_takeover`, so every message is compressed and inflated on its own.** Until 2026-11-17 the framework did not negotiate it at all, because with context takeover each socket keeps a compression window of 32 KiB or more, about ten times the 3.6 KB an idle socket costs ([`docs/research/ws-idle/`](../research/ws-idle/report.md)), and a client cannot be made to pay that for a smaller frame. Athena asked for it for its chatty JSON (presence snapshots, collaborative Doc and Sheet operations, streamed agent text), which repeats the same keys. Decided 2026-11-17.

- **The handshake.** The server reads every offer in `Sec-WebSocket-Extensions` in order and takes the first it can meet: `client_no_context_takeover`, `server_no_context_takeover` and `client_max_window_bits` (with or without a value) are known, `server_max_window_bits` only as 15, the window Go's flate has. An offer with another parameter, a parameter twice, or a value with `=` where none belongs is declined (RFC 7692 section 5.1) and the next offer is tried; with none left the socket is plain. The answer is `permessage-deflate; server_no_context_takeover; client_no_context_takeover`: the second is allowed whether or not the client offered it, and the engine needs it, since it inflates each message with a fresh state.
- **What the server sends.** The frame `Socket.Send` or a Topic builds is a plain frame; `SendFrame` and `Broadcast` of the engine turn it into a compressed one when the socket negotiated the extension: RSV1 set, the payload deflated at `BestSpeed` with a sync flush and the four bytes `00 00 ff ff` taken off. A payload under `MinSize` (256 bytes by default), a frame that compressing does not make smaller, and every control frame are sent as they are, which RFC 7692 allows on a compressed connection. A Topic message is compressed once for all its sockets that negotiated, and shared as the plain frame is ([ADR 0038](0038-a-broadcast-is-framed-once-and-shared.md)).
- **What the server reads.** RSV1 on the first frame of a text or binary message marks the message compressed; on a continuation or a control frame, and RSV2 or RSV3 anywhere, it is still a 1002. A compressed message is assembled as any message is, charged to the same reassembly budget by its compressed size, and inflated when whole. **What it inflates to is held to the route's `MaxMessage`** (over it is a 1009, `message too big once inflated`), so a small compressed message cannot hold more than a plain one, and a text message is checked for UTF-8 after inflating (a 1007), since the Reader cannot check what is still compressed. Data that is not valid deflate is a 1007.
- **Memory.** A socket holds two booleans, beside `bin`, so `sizeof(WS)` is unchanged at 512 bytes (`TestTheLeavingFlagAddsNoBytesToAnIdleWebSocket`). A flate state is taken from a pool for one message and put back (`sync.Pool`, never reaching user code, [ADR 0008](0008-no-pooled-object-reaches-the-user.md)); about GOMAXPROCS of them are live at once. A Publish to sockets that did not negotiate allocates nothing more (`TestAPublishToManySubscribersBuildsTheFrameOnceAndCostsTheSameForOneAsForAHundred`): the shared compressed frame is made only when a target negotiated.
- **Cost, measured** on 2026-11-17, AMD Ryzen 7 9700X, Go 1.27.4, `BenchmarkDeflateAFrameOf4KiB` and `BenchmarkInflateAMessageOf4KiB` in `internal/engine/wsdeflate_test.go`, three runs of two seconds: a repetitive 4,516-byte presence frame becomes 112 bytes; compressing it takes 2.7 to 3.0 µs with 113 bytes and one allocation, inflating it 3.5 to 5.1 µs with 16 KiB and ten allocations. That payload repeats one record, which is the best case for deflate: a real message compresses less and takes longer, so the figure is a floor and not what an application will see. Per message, and only on a socket that negotiated: no axis of [ADR 0003](0003-the-trade-budget.md) moves for an app that does not turn it on, and for one that does the allocations of a typed JSON request are untouched (a WebSocket message is not that path). Throughput and p99 of a socket with compression on, and idle memory of a thousand compressing sockets over TCP, are not measured; they wait for the serial run.

**What it fails at.** It does not compress what is already compressed or small; the sender decides by size only and by whether the result shrank, not by content. Compression time is spent on the goroutine that sends (for a Topic, on the first socket's) while the message is built, so a very large message delays that Publish. Without context takeover the ratio is lower than with it, since each message is compressed alone; that is the price of a socket that costs no memory. Autobahn's compression cases (12.x, 13.x) have not been run (roadmap item 10).

**What was rejected.**

- _Context takeover, on or negotiable_: a window of 32 KiB or more for each socket, and one more reason for a client to hold the server's memory.
- _A per-route option_: the extension is negotiated for the connection before a route is chosen, and an app that opts in wants it for every message type it sends; a message too small to benefit is sent plain by `MinSize`.
- _Compressing in `Socket.Send`_: a Topic would compress once for each socket, and a plain socket would pay the check. The engine makes the one compressed frame per Publish.
- _Choosing a level_: `BestSpeed` is what a message sent while a user waits can afford; a level is a knob an agent would have to understand before it could change anything useful.
- _A server_max_window_bits below 15_: Go's flate cannot be given a smaller window, so such an offer is declined and the client gets plain frames.
